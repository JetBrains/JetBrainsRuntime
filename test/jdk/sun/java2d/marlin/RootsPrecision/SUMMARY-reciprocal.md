# Reciprocal roots (Blinn 2006/2007) in the cubic solver

Input domain assumed throughout: Marlin coordinates over the float/double range, |coord| from 1e-7 to
1e30 with either sign. Coefficients are built from those coordinates the way Curve.xPoints and
Curve.perpendiculardfddf build them, so they are correlated rather than independent.

## Why one direction cannot be enough

Reducing to the depressed cubic subtracts sub = a/(3d), the mean of the three roots. A root far below
that mean is reconstructed by cancelling |sub|/|root| digits away. Measured over the roots this solver
used to drop (WhyLost.java): median |sub|/|root| = 3.4e12 for lost roots against 0.016 for kept ones,
with 21.2% of lost roots needing more than 16 digits of cancellation against 0.02% of kept.

A root is a ratio, not a number (Blinn, "How to Solve a Cubic Equation, Part 5: Back to Numerics",
IEEE CG&A 2007). Each direction is accurate only for the roots comparable to its own root-mean:

    d t^3 + a t^2 + b t + c     accurate for the LARGE roots
    c s^3 + b s^2 + a s + d     roots s = 1/t, accurate for its own large s, hence for SMALL t

So both are solved and the candidates pooled. Structure now:

1. cubicRootsRaw on (d,a,b,c): branch from the critical-point discriminant sign, closed-form roots,
   one compensated-Horner Newton step against that polynomial.
2. cubicRootsRaw on (c,b,a,d): same, giving s; candidates t = 1/s for s != 0 and finite.
3. Pool, skipping candidates already present within 8 ulps.
4. One more compensated-Horner Newton step on the original cubic for every candidate.
5. Drop duplicates the refinement merged, and candidates failing a scale-free residual check.

Two Newton passes are required, not one. Refining s against the reversed cubic is far better conditioned
than refining 1/s against the original when s is large, and a near-double root needs both passes to
converge. With the per-direction pass removed and only the pooled pass kept, the correctly rounded share
at a root gap of 1e-6 collapses from 98% back to 40% -- the same value as before any of this work. That
mistake was caught only by extracting the committed methods verbatim into FinalHelpers.java and
re-scoring them, rather than trusting the prototype's numbers.

## Results, scored against exact roots, N = 30000 per shape

| shape | before | after |
|---|---|---|
| xPoints, coords 1e-7..1e30 | 0 lost, 0 spurious, 100.00% <=0.5 ulp | 0, 0, 100.00% |
| **perpendiculardfddf, coords 1e-7..1e30** | **60 lost**, 84 spurious, 97.60% | **18 lost**, 72, **98.95%** |
| xPoints, coords 0..4096 | 0, 0, 100.00% | 0, 0, 100.00% |
| 3 roots in [A,B) | 0, 0, 100.00% | 0, 0, 100.00% |
| close pair, gap 1e-6 | 4 lost, 2 spurious, **40.46%** | 6 lost, **0**, **97.91%** |
| wild coefficients, 20 decades | 2141 lost, 999 spurious, 88.30% | 2318, **0**, **98.66%** |
| wild coefficients, 30 decades | 1834, 854, 91.90% | 1927, **0**, **99.34%** |

On the two shapes that correspond to real Marlin input at the stated coordinate range, the change wins on
both metrics: perpendiculardfddf loses 70% fewer roots and returns fewer non-roots than before.

## The one trade, stated plainly

The residual check (isRoot) removes candidates whose residual exceeds 1024 * ulp of the largest term of
the evaluation. On correlated Marlin coefficients it costs nothing -- lost roots are identical with and
without it -- and it halves the spurious count. On INDEPENDENT wild coefficients over 20 decades it
rejects some genuine but ill-conditioned roots: lost 2005 without the check against 2318 with it, while
spurious falls from 866 to 0.

Threshold sweep on that shape (N = 15000): none 1003/432, 1024 ulp 1160/0, 1e6 ulp 1113/0, 1e12 ulp
1024/8, 1e18 ulp 1003/432 (lost/spurious). On perpendiculardfddf lost is 9 at every setting and spurious
is lowest at 1024, which is why 1024 was chosen.

Dropping the check is a one-line change and is the right call if independent wide-range coefficients ever
matter: for Marlin a spurious root costs one harmless extra subdivision, while a lost root is a rendering
artifact, so the asymmetry favours keeping every candidate. It is kept here only because on the actual
input shapes it is free and strictly better.

## Verification

sun.java2d.marlin compiles clean. The scored methods were extracted verbatim from the committed
Helpers.java (FinalHelpers.java, regenerated by FinalCheck's extraction step) so the numbers above
describe the shipped code and not a prototype. No NaN or infinite root over any shape, 30000 polynomials
each, including coordinates at 1e30 and coefficients over 30 decades.

Still no jtreg run: that needs a full JDK build this workspace cannot do. The reciprocal solve roughly
doubles the cost of a cubic solve (a second cubicRootsRaw, one extra Newton pass, the residual check),
which is real and unmeasured -- worth a JMH pass on Stroker/Dasher before this lands.
