**The rebuilt capture routine verified on Windows (README "status of the other platforms").** What it took:

- `env.sh` resolved the Windows image as `build/windows-*-skia/images/jdk`, which on this VM is the frozen jbr25 image
  (`windows-aarch64-skia`), not the main-line one (`windows-aarch64-skia-main`): the first verification run launched the IDE
  on jbr25 and a Windows Security prompt for that java's built-in server took the foreground (the driver refused, as it
  should). `env.sh` now prefers a `windows-*-skia-main` image when one exists; the x64 machine's single image is unaffected.
- The kit's default IDE (`$LOCALAPPDATA/Programs/IntelliJ IDEA`) is 2026.2.4 here; the scenes, the seed and the plugin's APIs
  are 2026.3's (`IntelliJ IDEA 2`). `IDE=` and `IDE_HOME=` point there; worth a note in the README for machines with two installs.
- `IdeScenes` built the plugin's request URI without percent-encoding; the Windows terminal line has spaces (the Mac's is
  `ls`), so the first scene threw `URISyntaxException`. Spaces are encoded now.
- The wrapper's `arm.txt` carried a file-name prefix (a two-file `grep`; `-h` now) and grepped a `scenes.log` the
  plugin-driven driver no longer writes (guarded).
- The Windows text arms of the VM's rounds were not in the kit's wrappers: T0, T1, T4, T5, T6, S5, F5 added to
  `run-ide-win.sh` / `run-scenes-win.sh` in the six-dimension spellings (T1 = `blend=corrected darkening=none`, T4 = the
  default, F5 = `paragraphs=skia`). `text-reference/win/run-win.sh` speaks the new spellings, drops the retired smoothed and
  darkened emulation arms (their spellings read as coverage now) and builds no viewer (machines deliver trees); its
  built artefacts (`dwref.exe`, `classes/`, `fonts/`) are ignored by a new `.gitignore`.
