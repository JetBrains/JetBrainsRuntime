**Skia on native Vulkan (`sun.java2d.skia.graphiteApi=vulkan`): built, test first, the Skia jtreg set on it: 48 of 55 run lines pass, one real finding (twopass LCD)**

- Naming first (user's request, option (a)): the Windows platform layer is API-neutral now
  (`Win32SKPlatform.h/.cpp`, `Win32SK_*`, `Win32SKConfigInfo`, `Win32SKSurface`, commits `217410fa36f`,
  `bda5fc3ad81`); Dawn behind it as `DawnSK_*`, Vulkan as `VKSK_*` (`VKSKPlatform.h/.cpp`), as JBR's
  own Vulkan pipeline spells it (`VK*`). The property names the Graphite API, without a platform:
  `dawn` (default) or `vulkan` on Windows, `metal` (only) on macOS; other values leave the default
  (a warning with `sun.java2d.skia.verbose`). Description: `Skia m156 Graphite/Vulkan on NVIDIA
  GeForce RTX 3080 Ti (Vulkan)`.
- Design: `vulkan-1.dll` loaded at run time (nothing links against it), Vulkan 1.3 on the 3080 Ti,
  device extensions `VK_KHR_swapchain` and `VK_EXT_device_fault` (the driver does not offer
  `VK_EXT_rasterization_order_attachment_access`), Skia's VMA allocator
  (`VulkanMemoryAllocators::Make`, in `skia.lib` without a header). Each surface owns a VkImage;
  Graphite draws a window surface's client area into the next swap chain image itself (wait on
  acquire, signal render-done, leave it in `PRESENT_SRC_KHR`), then `vkQueuePresentKHR`; mailbox,
  else immediate, else FIFO, as Dawn chooses. Build: `-DSK_VULKAN` and Skia's bundled Vulkan headers
  in `lib-skia.m4`. Commit `119f3f7c601` (local).
- `SkiaGraphiteApiTest` (default, `dawn`, `vulkan`, `metal`; the description, then a window's first
  paint, its origin, a repaint and a resize on screen): red before (the `vulkan` line got Dawn),
  green after. Along the way: Graphite refused the swap chain images with only colour-attachment
  and transfer-destination usage (`validate_backend_texture failed`); they need the input-attachment
  usage, as Skia's own Vulkan window context asks for.
- The Skia jtreg set (`run-jtreg-skia.sh`, `build/skia-eval-out/jtreg-vulkan`) with
  `JTREG_EXTRA_OPTS=-Dsun.java2d.skia.graphiteApi=vulkan`: 48 pass, 7 fail. Four are the forced
  property overriding tests that expect Dawn (`SkiaDawnBackendTest` x3, `SkiaGraphiteApiTest Dawn`),
  one is upstream (`SkiaFontScalerMetricsTest`, as on Dawn). Device-loss recovery (transient and
  persistent) passes on Vulkan. The same build on Dawn (`jtreg-dawn-vkbuild`): 54 pass, only
  `SkiaFontScalerMetricsTest` fails; the refactor changes nothing there.
- Finding: `lcd=twopass` on Vulkan (`LcdTextBackgroundsTest skia 32 64`, `LcdTextLayersTest skia 32`
  red; blend and accumulate green). Rendering the test's cases on both APIs and diffing
  (`build/tmp/lcdprobe`): 44 pixels per text image differ, always single columns where neighbouring
  glyphs' inked extents overlap, i.e. the quads the batch moves to an overlap layer
  (`SKQuadBatch::push`, `splitOnOverlap`). There Vulkan shows only the first pass: on white the
  multiply, on black exactly 0 where Dawn has the added colour. The layer's second pass (kPlus,
  colour x coverage) has no effect. Not draw ordering: `ContextOptions::fAvoidDepthMode` and
  `fUseDrawListLayer` (tried, reverted) change nothing; not the extension above; not the pipeline
  cache (off, fresh and shared all fail). A plain VolatileImage with one string and no overlap is
  identical to Dawn. Open; candidates are in Graphite's Vulkan command recording (the layer's draws
  repeat the base draws' two pipelines with identical uniforms). Twopass is the Windows default, so
  arm A8 below measures it with this defect (44 pixels of a few thousand).

**Correction to the JBR Vulkan numbers above: its pipeline skips work on LCD text and on AA parallelograms; on the 37 RenderPerfTest tests where every pipeline draws the same pixels it is still 3.3x Skia on Vulkan**

- Source (`VKRenderQueue.c`, `VKRenderer.c`, `VKSurfaceData.java`, JBR as built here):
  `DRAW_AAPARALLELOGRAM` only logs its parameters; `FILL_AAPARALLELOGRAM` draws without coverage
  (`// TODO this is not AA!`); the glyph list is "a quick and dirty implementation of greyscale-AA
  text rendering over MASK_FILL" with LCD a TODO, and `VKSurfaceData` keeps the default
  `canRenderLCDText` (no LCD loop for its surface type), so LCD requests render greyscale. The
  configuration claims `CAPS_PS30`, so antialiased rectangles, lines and parallelograms take that
  path. Sync is honest: `VKRenderer_Sync` waits for the renderer's last GPU checkpoint.
- Probe (`build/tmp/lcdprobe/AaProbe.java`, one opaque VolatileImage per pipeline): LCD text has
  559 coloured pixels on software, Direct3D 9 and Skia, 0 on Vulkan (387 pixels inked against 608);
  an AA line has 230 partial pixels (Skia 176), Vulkan 0; AA rectangle outlines (1 px and 3 px)
  draw 130 / 390 pixels everywhere, nothing on Vulkan; an AA rotated fill (general shape, mask fill)
  is identical on all four.
- RenderPerfTest `rpt-skvk` re-scored: on the 28 tests whose names involve AA or LCD (a superset of
  the affected ones; it also holds AA ovals, which Vulkan draws honestly and slowly by mask fill)
  JBR Vulkan is 3.37x software; on the other 37 (plain geometry, non-AA and greyscale text, blits,
  XOR), where the outputs agree, **2.07x software and 3.30x Skia on Vulkan** (Skia on Vulkan 0.63x
  software there, on Dawn 0.49x). The morning's "LcdText 1000 lines 4.23 ms" and GlyphChurn LCD
  figures measure greyscale text and are not comparable; the IDE scene arm R2 (LCD editor text,
  AA outlines) is optimistic by an unknown share.
