**JBR 8 tried an asynchronous end-of-paint flush once (JetBrains/jdk8u_jdk, 2017-11 to 2018-04): what it was, why it went, what it teaches the hand-off**

- Not in OpenJDK: no `flushNow` with a sync parameter in any OpenJDK line (this repository's history from the 2007
  initial load, JDK 8 included; jdk8u's and jdk6's OGLRenderQueue). The native OpenGL queue's `sync` flag (a SYNC op
  ends the flush with `glFinish` instead of `glFlush`) is about the GPU, not the caller, and is unchanged since 2007.
  JBR 11+ changed OGLRenderQueue once more (JBR-2139, 2020: a 100 ms wait, then a toolkit-aware wait, against a
  deadlock with AppKit's main thread on macOS), no sync parameter.
- JBR 8, by Alexey Ushakov, macOS OpenGL:
  - JRE-578 "OGLRenderQueue.flushNow() executes too many times" (5762188, 2017-11-15; the report: 23-25 K flushes a
    minute when scrolling or typing with autorepeat, 100-120 % CPU). `RenderQueue.flushNow(boolean sync)`: `true` (the
    default) set `needsFlush` without `notify()` and waited, the flusher polling every 4 ms (`FLUSH_THRESHOLD`), so
    every synchronous flush waited up to 4 ms; `false` set `needsFlush` and returned at once. One caller used `false`:
    `LWComponentPeer.flushOnscreenGraphics()`, the macOS peers' flush at the end of an AWT paint (LWRepaintArea) and
    of window updates (LWWindowPeer): the same role as Swing's end of paint for us.
  - JRE-625 "Unstable UI menu rendering" (reported on the first build with it, CLion and IDEA 2018.1 EAP, macOS 10.13):
    menus, context menus, completion popups and Search Everywhere "aren't rendered at once"; linked to JRE-610 (visual
    glitches in popups). Fixed by abf35dc (2018-01-18) "Removed lazy flushing in flushOnscreenGraphics": back to
    `flushNow()`.
  - Laurent Bourgès on the commit (2018-02-27 to 03-26) and in 6af002a: without the `notify()` synchronous flushes are
    10-20 % slower on Linux; and with `sync=false` "who has the AWT lock?": the flusher takes the queue lock itself only
    for its timed flush (`tryLock()` runs only when `needsFlush` is false), so a flush asked for without waiting ran on
    the live buffer while the caller, the lock released, went on writing and clearing it. That is a race on the buffer,
    a plausible cause of half-drawn popups (inferred; JRE-625 names no cause).
  - JRE-690 "Recent bundled JDK VCS Log UI slowdowns" (macOS, scrolling and selection in the VCS log much slower than
    in builds before JRE-578): 45cbdc7 (2018-03-20) `QueueSyncType {NO_SYNC, SYNC, SYNC_NOW}`, the blits waking the
    flusher at once; 8aa2d04 (03-23) "NO_SYNC mode is not used", removed; 9b80de4 (04-03) "Removed flush threshold
    logic, it is not so useful after latest optimizations"; the author on the commit (04-11): "Finally, I've reverted
    the code to original logic", the synchronization in some blits having caused too many performance regressions.
    Merged into the line on 2018-04-17 (0b3f4fd).
- What it teaches the hand-off (`sun.java2d.skia.asyncPresent`):
  - The goal and the place were the same: the end-of-paint flush, without the painting thread waiting. The mechanism
    was not: JBR 8 left the request in the live buffer for a flusher holding no lock; the hand-off copies the buffer
    and its references under the lock (`RenderBuffer.copyTo`), the caller's buffer is empty when it returns, the flusher
    runs only the copy, the native entry points are serialized (SKBackend_EntryMutex), at most one hand-off is in
    flight, and every synchronous flush, sync and Robot read waits for it first. The race behind JRE-625 cannot occur
    in that form; `SkiaHandOffTest` holds a hand-off in flight to check the data dependencies that would show it.
  - The path differs too: JBR 8 made the AWT peers' paint flush lazy, the one we keep synchronous since the API split
    (`commit()` for the peers' paint events, `commitLater()` from Swing's RepaintManager only).
  - Never delay the wake-up of a flush someone waits for: the 4 ms poll cost 10-20 % and the VCS log regression. The
    hand-off wakes the flusher at once; the timeout flush stays at 100 ms and is not taken for a pending hand-off.
  - What remains of JRE-625's symptom class for us: a frame shown later than with a synchronous flush, by the
    encoding time. A popup's first frame is the case to watch: a window shown, then painted through Swing (commitLater)
    while its peer's first expose paints synchronously. Worth a test: open and close heavyweight popups and menus in a
    loop with a hand-off held in flight, and check every frame complete in Robot captures (Robot syncs first).
  - It was found by users, on many Macs, in EAP builds, and judged by anecdote (+30 % on one machine, -10-20 % on
    another). The hand-off has deterministic tests and n = 5 A/Bs, but on one machine; before it is on by default it
    needs the other machines' runs and the stress and soak steps (2026-11-04: steps 3 to 5).

**Parked, for the ledger: the asynchronous end-of-paint flush (the hand-off) as a future path, outside the Skia evaluation's scope**

- Decision (2026-11-05): the hand-off is not pursued further within the Skia evaluation, which is complex enough; no
  more changes or risk for it here. What is on the branch stays as it is, off by default: the hand-off
  (`sun.java2d.skia.asyncPresent`, `SKRenderQueue.flushForPresent` / `handOff`, `RenderBuffer.copyTo`), the native
  entry mutex (SKBackend_EntryMutex), the test hooks (`sun.java2d.skia.test.handOffDelay`, `.handOffError`), and the
  API split in shared AWT classes (`BufferedSurfaceDataExt.commitLater`, `WindowPeer.updateWindowLater`,
  `AWTAccessor.WindowAccessor.updateWindowLater`, `Window`, `WWindowPeer`, Swing's `RepaintManager`). The split's
  defaults keep every other pipeline exactly as before, but it touches shared AWT code: a candidate to revert if the
  branch's footprint outside the backend has to shrink, and for an AWT owner's review if the path is taken up.
- What it showed (x64hw, A8, n = 3 after the race fix, 2026-11-04): the EDT's paint -32 % typing (9.43 -> 6.41 s) and
  -28 % UI (13.29 -> 9.61 s), its flush wait 3.25 -> 0.29 s and 4.11 -> 0.67 s; presents and flusher time +5 % / +3 % in
  the UI scenes, typing latency p90 8 ms on both. Guarded by `SkiaAsyncPresentTest`, `SkiaHandOffTest` (sources,
  dispose, strikes, sync, error), `SkiaCommitLaterTest`, `SkiaRobotHandOffTest`. Prior art: JBR 8's lazy
  `flushOnscreenGraphics` (above), reverted for half-drawn popups (JRE-625).
- Next steps if it is taken up, in order:
  1. The JRE-625 scenario as a test: open and close heavyweight popups, menus and completion-like windows in a loop with
     a hand-off held in flight, and check every Robot capture shows a complete frame (Robot syncs first).
  2. Entry-point lint and a debug assertion: every native entry point under the entry mutex; none reached on another
     thread while a hand-off runs.
  3. Stress tests: windows created, resized, hidden and disposed during hand-offs; deadlock tests for the lock order of
     the flusher's monitor, the AWT lock and the toolkit thread (cf. JBR-2139's deadlock with AppKit).
  4. OpenJDK's AWT and Swing jtreg groups with the property on and off.
  5. Scene-capture diffs, hand-off against synchronous, and a daily IDE soak; runs on the other machines (the Mac, the
     VM), not one.
  6. The remaining +5 % presents and +4 % recordings in the UI scenes.
- Does it need Skia? No. The benefit grows with the cost of the flush the EDT waits for (Graphite's per-draw and
  per-recording work makes ours large), but nothing in the mechanism is Skia's:
  - Generic already: the copy of the buffer and of the queued ops' references lives in `sun.java2d.pipe` and works
    for any `RenderQueue`; the API split is pipeline-independent and defaults to the synchronous call; Robot syncs
    the toolkit before every read; the data dependencies (software sources, read-backs, disposals, font strikes)
    are met by the synchronous flushes every BufferedRenderPipe pipeline already makes at those points
    (OGLBlitLoops' "flush immediately" sites and their D3D, Metal and Vulkan equivalents), which wait for a hand-off
    first. The GPU side is no obstacle either: like Graphite, the direct pipelines copy what a frame needs into
    their own vertex and upload buffers while encoding, and glyph images are freed through `flushAndInvokeNow`.
  - What each pipeline would need, the Skia backend had it easier:
    - Native entry points that rely on the AWT lock keeping the flusher out: the Skia backend is one library with about
      twenty JNI entries behind one mutex; the OpenGL, Direct3D, Metal and Vulkan pipelines have more entries and calls
      from other threads (D3D device resets on display changes, Metal's display-link thread blitting the layer,
      Wayland's frame callbacks for Vulkan), each to audit and serialize.
    - A flusher thread to hand off to: OpenGL, Direct3D and Metal have one; JBR's Vulkan pipeline flushes on the
      calling thread (the EDT) and would need one first, the largest change of the four.
    - A place to hand off: Skia and Vulkan end a window's paint cycle with `BufferedSurfaceDataExt.commit()`
      (FLUSH_BUFFER); OpenGL and Direct3D present through Swing's back buffer blit to the window, whose
      "flush immediately" in the blit loops would become the hand-off point; Metal with display sync already presents
      from the display link, off the EDT, so only the encoding would move.
  - Expected gain elsewhere, from data at hand: JBR Vulkan's whole flush, which it runs on the EDT, was 2.0-2.2 s per
    typing launch (R2, 2026-11-03), against Skia/Vulkan's 3.2 s wait: less to win, but not nothing. Direct3D 9's flushes
    are shorter and its present does not wait. Measure the EDT's flush wait per pipeline before choosing one.

**Draft for the ledger (user's question, 2026-11-05): the value proposition of the Skia paths on Windows as of now, and a route to shipping one**

- Baseline that matters: the IDE on Windows renders with the software loops today (D3D off by default, Vulkan gated).
  Against them every GPU path is a large win in EDT paint: Direct3D 9 / JBR Vulkan 1.5x typing, 1.6-1.8x UI (s1);
  Skia/Vulkan 10.06 / 13.41 s and Skia/Dawn-D3D11 10.28 / 13.98 s (s18) against the loops' 12.17 / 20.32 s (s1; across
  series, loosely). Against JBR Vulkan on this discrete GPU Skia is behind in flush time (1.53x typing, 1.20x UI, s18),
  partly because JBR Vulkan takes shortcuts (LCD drawn greyscale, AA outlines missing); like for like on text 1.23x.
  Typing latency is equal everywhere (p90 8-10 ms). On macOS Graphite/Metal is ahead of JBR's Metal by 12-17 % of paint
  after Metal's glyph-cache fix (ledger §11.17).
- 1. Beyond a backend: Skia offers the raster backend (R0: -3 to -7 % EDT paint against the loops, the loops'
  semantics), analytic GPU shapes (2.2-3.5x over Marlin tiles), and text: scaler (metric-exact), shaper (layout-neutral
  against Java's), paragraph engine, DirectWrite-hosted masks within 4-6 levels of native (the VM). Value: one engine for
  GPU and CPU output, capabilities the platform lacks (effects, rich text, colour fonts). Cost: each layer is its own
  fidelity decision (text above all), and its own performance profile (Skia's text path is 2.5-3x Java's glyph-image
  path in colour-churn regimes, §19b). For shipping, these are options to stage after a backend, not part of it.
- 2. Breadth: one backend reaches Graphite/Vulkan, Graphite/Dawn on D3D11 (and D3D12) and the raster backend. Dawn/D3D11
  is the one route JBR's plan lacks: machines where Vulkan is absent, weak or blocked (VMs, Windows on ARM, some
  integrated GPUs, possibly RDP), and Chrome ships Graphite on Dawn/D3D11 by default on Windows since Chromium 158, which
  brings its driver workarounds and GPU blocklist. Unmeasured: how many seats that is (no telemetry), whether Dawn beats
  the loops there (the Parallels VM: RenderPerfTest 1.03x GDI, a wash), RDP and WARP (Graphite is reported not to run on
  WARP), and integrated GPUs at all.
- 3. Completeness: the numbers are concrete for one discrete-GPU machine and paced IDE scenes; missing are integrated
  GPUs, weaker CPUs, startup, memory, power, robustness. Where Google's tuning helps us is where we use Skia's higher
  layers (shapes, text runs, effects, pipeline caching, drivers), not the small-op stream: the floor there is measured
  (about 0.4-0.8 µs per draw on Graphite and Ganesh alike) and is not something unseen tuning removes. IDE frames are
  not simpler than web content (1 000-1 800 ops); what differs is the granularity Java2D hands over (one op at a time,
  text as glyph images), so Chrome's batched glyph runs and display lists do not reach us.
- 4. Skia's quality against the Java backends': the Java backends had real gaps (Metal's 256-cell glyph cache stalling,
  JBR Vulkan's LCD and AA shortcuts, D3D9 off, OpenGL deprecated), and Skia brings correct LCD and AA, effects and a
  maintained driver layer. But the gaps were cheap to fix where tried (the glyph-cache fix recovered 60-80 % of Metal's
  gap), the direct backends' small-op path is inherently cheaper, and Skia's quality is not free for us: the evaluation
  had to find and work around a dozen Graphite behaviours (whole-pass MSAA, AA on non-aligned rects, kPlus shader blend on
  Vulkan, Dawn's features unrequested, no dual-source output, linked-image flushes, per-sprite drawAtlas).
- 5. Ceiling and "inlining": the overhead is per draw inside Graphite's device and has no public way around it. Inlining
  would mean a Skia fork with our own render steps, which gives up the reason to use Skia; if the ceiling binds, the
  answer is a direct backend (path c), not a hollowed-out Skia. Within the rules: fewer draws (batching, the image
  atlas), the hand-off (parked), upstream requests (§15: storage buffers on Vulkan, drawAtlas batching). Likely to bind:
  not in paced latency, possibly in CPU and power headroom on weak machines and very large repaints, which is exactly
  the unmeasured part.
- Route (gated; abort is a valid outcome at every gate):
  - Gate 0, leadership: a Windows rendering path that cannot go upstream (Skia is JBR-only) is acceptable. If not, stop.
  - Phase A, data that decides (about 4-6 weeks): seat telemetry (GPU vendor and driver, Vulkan availability, D3D
    feature level, VM, RDP, ARM); the all-arms series (A0, R0, R1, R2, A2, A8; n = 5) on an integrated GPU (the 5600G's
    Radeon), an Intel laptop and a Snapdragon machine, with startup, memory, power; the fidelity-fair comparison with JBR
    Vulkan; robustness (device loss, TDR, display and DPI changes, sleep, RDP switch).
  - Gate 1: go if Dawn reaches a material share of seats Vulkan cannot, or Skia is clearly better than the loops and JBR
    Vulkan on integrated GPUs, and no blocker; otherwise record the conditions to revisit and stop.
  - Phase B, path b on Windows only (about 2-3 quarters): a JBR-owned Skia build and publication, a size budget,
    isolation from Skiko's copy; the fallback ladder Graphite/Vulkan, Graphite/Dawn-D3D11, raster or loops, with a
    blocklist; correctness gates (OpenJDK java2d/awt jtreg, the scene corpora, DirectWrite text parity); defaults (LCD
    mode, present=cycle, no Swing back buffer, image atlas); startup (pipeline cache, precompile); opt-in for EAP users
    with crash, device-loss and frame-time telemetry. Out of scope: Skia's text stack, the hand-off, other platforms.
  - Gate 2: the EAP opt-in data. Phase C: default on for a share of Windows EAP users, staged, fallbacks kept, then a
    release.
