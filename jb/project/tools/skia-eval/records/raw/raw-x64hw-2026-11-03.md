  by side across colour changes.)

**Optimization 2: on Vulkan a window's present is drawn inside the flush's recording (`9b8a453074d`)**

- Before: every present was a second recording (draw the window surface into the swap chain image, snap, insert
  with the semaphores, submit) after the flush's own (A8 typing: the present's "copy" span 307 ms per launch).
  Now `EndOfFlush` acquires the image before the submit, draws the window into it in the window's context, and
  the context's recording carries the semaphores and the present layout: one recording, one submit per frame.
  One window per context and flush, others as before.
- Found on the way, test first: under `present=cycle` a window drawn in an earlier flush is presented in a flush
  that drew nothing into its context, which then was not submitted, so the folded present was dropped:
  `SkiaPresentCycleTest` on Vulkan red (the first paint never reached the screen), green once such a context
  joins the flush's submit. `SkiaGraphiteApiTest` (Vulkan, a resize) and the present-cycle lines on Dawn pass.

**How the Skia prebuilt is compiled (JetBrains/skia `tools/skia_release/build.py`, branch skiko-m156, and Skia's own `gn/`)**

- Windows x64: `is_official_build=true` (Skia's `optimize` config: `/O2 /Zc:inline`, `/OPT:ICF /OPT:REF`; macOS
  and Linux get `-O3`), clang-cl (`clang_win`, as Skia recommends on Windows), `is_trivial_abi=false`, no CPU
  target beyond baseline x86-64 (`-msse2 -mfpmath=sse`; Skia's raster code dispatches SSE4.1/AVX2 at run time,
  Graphite's CPU side does not), no LTO, Dawn D3D11 + D3D12, Vulkan, the GPU parts as extensions
  (`skia_gpu_as_extension`). Debug checks are off (official build); Dawn's WebGPU validation is compiled in and
  runs on every call (a runtime toggle can skip it, below).
- What a custom build could change, none of it tried yet: `-O3` (clang-cl `/clang:-O3`), `-march=x86-64-v3`
  for Graphite's CPU paths, ThinLTO (the release's static libraries are linked by MSVC's `link.exe` in the JDK
  build, which cannot read LLVM bitcode: `libawt_skia` would have to link with `lld-link`), `is_trivial_abi=true`
  (`sk_sp` in registers; only if `libawt_skia` is compiled with clang-cl too, the MSVC ABI would break). Typical
  gains of such flags on CPU-bound C++ are in the 5-15 % range, so 0.2-0.4 s of the 3.5-4 s flusher at best.

**Optimization 3: batched quads are clipped on the CPU, rect clip changes no longer draw the batches (`56afa4361c3`), test first**

- `SkiaClipBatchTest` (new): 40 tokens, each under its own clip (every third cutting its last glyph), and filled
  rects under cutting clips. Red before: 20 glyph batch draws (limit 4); text within 8 levels of the software
  loops, rects exact. Green after: 1 batch draw, the same pixels.
- Design: batched axis-aligned quads are clipped to the rect clip as they join a batch (texture coordinates
  mapped along); the canvas clip is applied lazily (a clip change marks it stale; a batched op opens the canvas,
  an op drawing through the canvas draws the batches and applies the clip). Shape clips, transforms, slanted
  quads and rings across the clip, and rect batches with a shader paint keep the eager path.
  `J2D_SKIA_EAGER_CLIP` restores the old behaviour.
- RenderMatrix, lazy against eager on one image: first one cell differed, `xf:SCALE_2/TEXTURE/FILL_RECT` (60
  pixels beyond 32, max 187; eager within 4 of the loops). Bisected with switches: the CPU clip, not the open
  canvas. Root: Graphite draws a texture-paint rect that covers exactly the whole surface differently from a
  larger one cut by the canvas clip — the same with the old code and an exact-fit rect (`build/tmp/matrix/
  TexRepro2`, 64x64 surface, fill 16..48 under scale 2: eager max 187, lazy max 4; fill 6..58: the reverse). The
  CPU clip made such exact-fit quads common, so rect batches with a shader paint keep the canvas clip. After
  that, all 1152 cells identical between lazy and eager. Open, for Graphite: the exact-fit texture fill (a
  pre-existing difference against the loops, rare in practice; needs its own red test and a look at
  Graphite's full-target draw handling).

**Dual-source blending in Graphite: what is true (m156, JetBrains/skia `24300fbbcb`, sparse clone in `~/Projects/skia`)**

- Graphite has it and uses it, as a shader capability per backend: Dawn sets it if the *device* has
  `wgpu::FeatureName::DualSourceBlending` (`DawnCaps.cpp:482`), Vulkan from `VkPhysicalDeviceFeatures::dualSrcBlend`
  of the features passed in (`VulkanCaps.cpp:333`), Metal always. Our Vulkan device enables every core feature
  (on); our Dawn device asked for `ImplicitDeviceSynchronization` only, so on D3D11 and D3D12 it was **off**,
  although both adapters of the RTX 3080 Ti offer it (`SKEnvironment.deviceFeatures`, below).
- Who uses it: blend formulas with a secondary output (`CanUseHardwareBlending`, `ContextUtils.cpp:44`), i.e. coverage
  with modes such as Src, Clear, SrcIn, and LCD coverage with SrcOver, which only Graphite's own text steps produce
  (BitmapText A565, SDFTextLCD). Without it: shader blending with a destination read (texture copy on Dawn).
- Who cannot: clients. No public API has a second colour output or LCD coverage: SkMesh and drawVertices emit colour
  only, runtime effects never see `sk_SecondaryFragColor`, any SkBlender forces a destination read. The only way in for
  Java's glyph images is a custom SkTypeface whose scaler context returns them as LCD16 (5/6/5) masks, mapping Java's
  strikes onto Skia's; Graphite then batches LCD text across colours (colour is a uniform in a storage buffer) and does
  the dual-source blend itself. Not tried.
- Side finding, the cause of the Vulkan twopass defect (2026-10-28): Graphite never blends kPlus in hardware where the
  destination is cheap to read (`ContextUtils.cpp:66`; Vulkan reads it as an input attachment, `VulkanCaps.cpp:1272`), so
  our second pass read the destination on Vulkan and the overlap layers lost it.
