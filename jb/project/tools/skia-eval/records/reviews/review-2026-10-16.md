# Review of `manuel.unterhofer/JBR-10654-skia-backend` (HEAD 8b49885afb11 vs `main`)

Date: 2026-10-16. Scope: the resulting tree of the 19 commits (59 files, +7507/-14), with the
per-commit history as context. Everything below was checked against the code at HEAD; items I
could not settle from the sources are marked **to verify** with the evidence that would settle
them. Severity: **bug** (wrong today), **risk** (wrong under a reachable condition, or a sound
property that rests on an unstated assumption), **nit** (quality). Two halves were read by
independent reviewers with narrow briefs (Windows; the Metal switches commit) and their
load-bearing findings re-verified by me against the source.

## 1. Shared native code (`share/native/libawt_skia`)

### Bugs

None found. The queue interpreter, the batch/flush ordering (glyph and mask batches are drawn
before any other draw, state change, destination change or `snap()`), the clip/transform
application (`applyCanvasState`: device-space clip before the matrix, `restoreToCount` to a
per-destination base), the composite mapping, the premultiplied-stop gradient interpolation, the
unpremultiply tables, the readback protocol and the `GetPrimitiveArrayCritical` pairing in the
direct entry points are correct.

### Risks

**R1. `SKBackend.cpp:197-203` with callers `:1688` (CopyArea) and `:1622` (SurfaceToSwBlit) —
risk (latent): re-wrapping the destination leaves `g.canvas` dangling.**
When `SKBackend_GetSurface` sees a replaced platform texture it flushes the batches and resets
`st->surface`; if `ops == g.dst`, `g.canvas` still points at the canvas of the surface just
released and is used by `SKBackend_CopyArea` three lines later and by every op until the next
`SET_SURFACES`. Not reachable today: on macOS `pTexture` is written once in
`MTLSurfaceData_initTexture` (before the Skia wrapper exists) and `MTLLayer.replaceSurfaceData`
creates a new surface per resize (`MTLLayer.java:86`); the Windows half also creates a new
surface per resize. *Fix:* in the re-wrap branch call `forgetSurface(ops, false)` and, in
`SKBackend_SetDestination`, take `g.canvas` after `GetSurface` (already the case) — i.e. make
`GetSurface` invalidate the render state it is about to break, or assert `ops != g.dst`.

**R2. `SKBackend.cpp:225-241` + `:1554-1566`, `:734-738` — risk (to verify, Windows only):
cross-context sources are wrapped with the destination's recorder regardless of device.**
A source from another `SKConfigContext` is submitted synchronously and then wrapped with
`g.cc->recorder`. That is valid only when both contexts share one GPU device: true on macOS
(every `MTLContext` opens the system default device), not necessarily with Dawn where each
`Win32SKGraphicsConfig` owns a `wgpu::Device`; WebGPU rejects a texture from another device with
a validation error that Dawn reports asynchronously (nothing is drawn, nothing fails). *Evidence:*
drag a window holding a cached `TexturePaint`/VolatileImage from one monitor to another on
Windows and check the uncaptured-error callback. *Fix:* when `src->state->cc != g.cc`, read the
source back and re-upload (or copy through the software blit loops) instead of `WrapTexture`.

**R3. `SKBackend.cpp:682-695` — risk (memory): the opaque-conversion buffer is static and sized by
`maxTextureSize()`.**
`static std::vector<uint32_t> opaque` is resized to the tile (`w*h`) and never shrinks. Tiles are
bounded by `recorder->maxTextureSize()` (16384 on Apple GPUs) and, when `g.hasMatrix` is set,
by nothing else (`:1504` skips the clip-to-visible step), so one transformed `drawImage` of a
large `TYPE_INT_RGB` image can pin up to 1 GiB (16384² x 4) for the life of the process, plus the
same again transiently in Graphite's upload buffer. *Fix:* cap the upload tile for the opaque
path (4096² is plenty), or make the buffer a local so it is returned after the blit, or drop the
CPU fill and upload `kBGRA_8888` with `kOpaque_SkAlphaType` (Graphite swizzles alpha to 1 for
opaque images; the comment's worry about "relying on" that is unfounded, it is part of the
`SkAlphaType` contract).

**R4. `SKRenderQueue.cpp:448-460` + `SKShapePipe.java:427-428` — risk (latent null
dereference): the direct `drawShape` entry has no `params` array.**
For `KIND_RECT/ROUND_RECT/OVAL` the Java side stores the geometry in `geo.params`, but the
`flushAndInvokeNow` path passes `geo.coords` (null for those kinds) and the native entry forwards
`coords` as `params` (`:459`), which `SKBackend_DrawShape` dereferences at `:1122`. Unreachable
today because the direct path is only taken when the op exceeds the 6.4 MB queue (`:406`), which
a 20-float analytic op never does. *Fix:* restrict the direct path to `KIND_PATH` (the only kind
that can be large) and assert, or add a `params` argument.

**R5. `SKBackend.cpp:1738-1742` + `:313-320` — risk (noise, benign): a `FLUSH_SURFACE`d window
stays in `g.touchedWindows`.**
`forgetSurface(ops, dispose=false)` keeps the entry, so the `SKBackend_EndOfFlush` of the same
flush calls `SKPlatform_RequestRedraw` on a surface whose layer was already cleared
(`MTLSKSurfaceData.invalidate -> clearWindow` runs before the op is enqueued), hitting the
WARNING trace at `MTLSKPlatform.mm:98` on every window close. *Fix:* erase from `touchedWindows`
on every release, not only on dispose.

**R6. `MTLSKSurfaceData.java:120-124` / `SKBackend.cpp:252` — risk (to verify): Metal frees the
texture after a non-blocking Skia submit.**
`SKSurfaceData.flush()` ends with `SKBackend_ReleaseSurface(ops, false)`, which submits with
`SyncToCpu::kNo`; `delegate.flush()` then runs Metal's `FLUSH_SURFACE`, which releases
`pTexture` (`MTLSD_Delete`, for off-screen types). This is memory-safe only because Graphite
retains the wrapped `id<MTLTexture>` in its `Texture` resource for as long as the command buffer
that uses it is tracked. *Evidence:* `MtlResourceProvider::createWrappedTexture` in Skia m156
uses `sk_ret_cfp` on the backend texture. If it does, say so at the call site; if not, submit
with `kYes` on release.

### Nits

- `SKBackend.cpp:1101-1104` — dead code: the `SkDashPathEffect` branch is unreachable.
  `SKShapePipe.render` strokes dashed shapes in Java and enqueues a fill (`SKShapePipe.java:194-203`),
  and analytic strokes require `getDashArray() == null` (`:174-175`). If reached it would also be
  wrong for odd dash arrays (`SkDashPathEffect::Make` rejects them). Remove it and the two dash
  slots of the stroke wire format, or keep the format and document them as reserved.
- `SKBackend.h:49`, `SKBackend.cpp:342, 1659, 1729` — `SKConfigContext::dirty` is written and never read. Remove.
- `SKRenderQueue.cpp:387-414` — the `ENABLE_*_OP`/`DISABLE_*_OP` skippers are dead (`SKDrawImage`
  never enqueues them, and the layouts were verified against `BufferedBufImgOps`). Either keep as
  defensive parsing with a one-line comment or let them fall to the `default:` error.
- `SKQuadBatch.h:159-163` — a batch mixing textured and untextured quads would hand
  `SkVertices::MakeCopy` a `texCoords` array shorter than `positions` (out-of-bounds read). Not
  reachable (each instance is used with one kind), but worth an `SkASSERT(texCoords.empty() ||
  texCoords.size() == positions.size())`.
- `SKBackend.cpp:736, 1556` — a cross-context source costs a full `SyncToCpu::kYes` stall per
  blit. Acceptable for a prototype; note it in the comment so it is not mistaken for a bug in a
  profile.
- `SKBackend.cpp:1504-1523` — with a non-identity transform the whole source rect is uploaded even
  when mostly clipped; mapping the clip through the inverse matrix would bound it. Perf only.
- `SKSurfaceData.cpp:65` — `J2dRlsTraceLn(J2D_TRACE_INFO)` per surface creation is fine
  (release traces print only with `J2D_TRACE_LEVEL`), but the Metal surfaces trace this at
  VERBOSE; match.

### Clean

`SKRenderQueue.cpp` opcode decoding matches the Java encoders byte for byte (checked
`DRAW_GLYPH_LIST`, `BLIT`, `SURFACE_TO_SW_BLIT`, `MASK_FILL`, `MASK_BLIT`, the gradient ops and
the shape ops). `SKGlyphCache` (eviction flush ends the recording before `writePixels`, cell chain
walk by `cacheInfo` and `glyphSubimage`), `SKMaskCache` (row staging, dirty span, wrap-around flush,
shader-paint tiles uploaded individually and mirrored into staging) and `SKQuadBatch` (16-bit index
splitting, colour promotion, white mesh paint under `kModulate`) are correct. `ReadbackRequest`
is sound (callback and caller on one thread; a never-delivered callback leaks one request, as
documented). JNI: no leaked local refs, critical arrays released on every path, no JNI calls while
critical arrays are held.

## 2. Java side (`share/classes/sun/java2d/skia`, macOS classes)

### Bugs

None.

### Risks

**R7. `MTLLayer.java:148-163` — risk (visual): presentation is not serialised with the Skia
queue.**
`drawInMTLContext` holds only the Metal queue lock; `SKBackend` submits mid-flush
(`ReleaseSurface`, cross-context sources, `SurfaceToSwBlit`), so `blitTexture` can copy a texture
that holds half of a Java frame. The Metal pipeline never presents mid-flush because the blit
runs under the same lock the flusher needs. The comment's lock-order argument is right, so the fix
is on the native side: keep `insertRecording` mid-flush and defer `submit` to `EndOfFlush` wherever
no CPU wait is needed (`ReleaseSurface(dispose=false)` for off-screen surfaces, the cross-context
path when the source is on the same device).

**R8. `MTLSKPlatform.mm:73-76, 89-103` vs `MTLSurfaceData.m:349-359` — risk (data race,
benign): `pTexture` and `layer` are read without the Metal lock.**
`clearWindow` writes `mtlsdo->layer = NULL` on the EDT (via
`MTLSKSurfaceData.invalidate -> delegate.invalidate`) with no lock at all, while the Skia flusher
reads it in `SKPlatform_RequestRedraw`. The stale-read outcome is harmless (the native `MTLLayer`
is released only in `super.dispose()`, after `flush()` returned, and `startRedraw` hops to the main
thread), and the Metal flusher has the same race with the EDT. Still a C-level data race on a
pointer. *Fix:* forward `invalidate()` to the delegate only after the Skia `FLUSH_SURFACE` has
run (i.e. from `MTLSKSurfaceData.flush()` after `super.flush()`), or make `clearWindow` go through
the Skia queue when Skia is on.

**R9. `MTLSKInterop.h:34-45` — risk (sync hazard): hand-mirrored copies of `MTLGraphicsConfigInfo`
and `MTLSDOps`.**
Verified identical to `MTLGraphicsConfig.h:46-49` and `MTLSurfaceData.h:38-43` today; nothing
enforces it. *Fix:* move the two plain structs into a header that does not pull Cocoa (there is
already `MTLSurfaceDataBase.h` for `BMTLSDOps`) and include it from both libraries.

### Nits

- `SKContext.java:46-48` + `SKSurfaceData.java:196-198` — `getContext()` is a `synchronized`
  static `WeakHashMap` lookup, called from every `BufferedContext.validateContext`, i.e. once per
  primitive batch; `MTLSurfaceData.getContext()` is a field read. Cache the `SKContext` in a final
  field of `SKSurfaceData`. Relevant for the perf run.
- `SKSurfaceData.java:232-233` — comment "(as Src, see SKBackend_SetXorComposite)" is stale; the
  native side draws XOR text through the XOR blender with glyph coverage, not as Src.
- `SKEnvironment.java:66-76` — `defaultsFor` has two identical branches; collapse until Vulkan or
  Dawn gets its own values.
- `SKRenderQueue.java` — a near-verbatim copy of `MTLRenderQueue` including the 100 ms timed flush.
  Precedent (OGL/MTL/D3D each have one) makes this acceptable; mention it in the PR so nobody asks.
- `MTLSKEnvironment.mm:33-39` — a throwaway `MTLDevice` is created for the description string
  (the Windows half does the same with a full Dawn device). Report the device of the first config
  instead, or accept and say so.
- `MTLSKPlatform.mm:31-33, 109-113` — `objc_autoreleasePoolPush/Pop` are declared by hand;
  they are indeed in no public SDK header (checked). `NSAutoreleasePool` (public, usable under
  MRC, which this library is) gives the same RAII scope without private symbols.
- `MTLSKPlatform.mm:85` — colour type is hard-coded `kBGRA_8888`; correct today
  (`MTLSurfaceData.m:79` uses `MTLPixelFormatBGRA8Unorm`), but reading `tex.pixelFormat` costs
  nothing and survives a Metal-side change.

### Clean

- Flag-off behaviour on macOS: `MacOSFlags` reads `sun.java2d.skia` directly and changes state
  only when it is `true`; `MTLGraphicsConfig` branches on `SKEnvironment.isSkiaEnabled()`, which
  with the flag unset returns `false` after loading one class; `getContext()` returns the same
  `MTLContext` object (only the static return type widened — all callers checked:
  `MTLSurfaceData.getContext` switched to `getMTLContext()`, `StrikeCache` uses `BufferedContext`;
  no other caller). `LWCToolkit.sync` adds the Skia sync inside the Metal branch only.
- `SKContext.validateContext` pre-invalidation is correct and necessary: `BufferedContext.validate`
  re-sends surfaces, clip and (colour) paint on a context switch but not composite, transform or a
  non-colour paint, and the native render state is one for all configs.
- Pipe selection (`SKSurfaceData.validatePipe`, `canRenderLCDText`, `getMaskFill`, `copyArea`
  refusing XOR) matches `MTLSurfaceData` condition for condition, including the JBR XOR-text branch.
- Lock pairing: every `rq.lock()` has a `finally { unlock }`; `SKSurfaceData.flush/dispose` are
  synchronous (`flushNow`) as in Metal, so the native ops are never freed with queued references.
- Lifetime: `retainedByOps` keeps the Metal delegate reachable until the Skia `DISPOSE_SURFACE`
  has run, and the entry is removed before `SurfaceData_DisposeOps` frees the Skia ops, so a
  pointer value cannot be reused while mapped. The Disposer-thread `currentContext = null` is
  under the queue lock, as in `MTLContext.disposeSurface`.
- Proxy cache: one per config, shared with the Metal surfaces of that config; with Skia on, no
  Metal surface is ever a Java destination, so the shared map holds only `SKSurfaceDataProxy`.
- `SKShapePipe`: wire format matches the interpreter; the normalizing iterator reproduces
  Marlin's; dashes and sub-pixel strokes are kept on Marlin, which is the right call for parity.

## 3. Windows half (`windows/native/libawt_skia`, `windows/classes/sun/java2d/skia`)

Reviewed by the Windows reviewer; B1 and B2 re-verified by me against the source.

### Bugs

**B1. `Win32SKScreenUpdateManager.java:40, 67-70` — bug (leak): the `WeakHashMap<WComponentPeer,
Win32SKSurfaceData>` never releases an entry.** The value holds `protected final WComponentPeer
peer` (`Win32SKSurfaceData.java:38`), a strong path from value to key, so the weak key is never
cleared and `dropScreenSurface` is a no-op by design. Every closed window retains its peer, target,
surface, Dawn texture and configured swap chain on a destroyed HWND for the life of the process.
*Fix:* drop the map. During `createScreenSurface`, `peer.getSurfaceData()` still returns the
surface being replaced (`WComponentPeer.createScreenSurface` assigns the field only after the
manager returns), so `previous = peer.getSurfaceData() instanceof Win32SKSurfaceData w ? w : null`
gives the hand-over source without manager state.

**B2. `DawnSKPlatform.cpp:237, 254, 274` — bug (shadowing): the local `opaque` shadows the
parameter stored at `:177`.** `configuration.alphaMode` is therefore decided by what the swap
chain supports, not by whether the Java surface is opaque, and `DawnSKSurface::opaque` has no
reader. MSVC warns C4456 here. *Fix:* rename the local to `opaqueSupported`, use
`opaque && opaqueSupported ? Opaque : Auto`, and either read `surface->opaque` or remove the
field and the `isOpaque` JNI parameter.

### Risks

**R10. `DawnSKPlatform.cpp:206-211, 226-232, 276-279` — risk (to verify): Dawn failures are not
detected, so there is no GDI fallback.** Dawn returns error objects, not null, for failed
`CreateTexture`/`CreateSurface`/`Configure`; the `== nullptr` checks never fire (the code
acknowledges this at `:277-279`). An oversized texture or a second swap chain on an HWND yields a
surface that cannot present and a WARNING at `:343` on every flush. *Fix:* bracket creation and
`Configure` in `PushErrorScope(Validation)`/`PopErrorScope` + `WaitAny`, return null on error, and
check `width/height` against adapter limits first. *Evidence:* Dawn `Device.cpp` `APICreateTexture`
returning `TextureBase::MakeError` on validation failure.

**R11. Two flip-model swap chains on one HWND — risk, three entry points.**
(a) `Win32SKGraphicsConfig.java:187-193`: `createSurfaceData(peer, 0)` passes `previous = null`
(a new `wgpu::Surface` for an HWND that may still hold a configured chain); unreachable with the
manager installed, so dead and dangerous, and its Javadoc describes a situation that cannot occur.
(b) `Win32SKScreenUpdateManager.java:45-48`: with `bbNum != 0` the window goes to GDI, but the old
chain stays attached until GC + Disposer because `FLUSH_SURFACE` does not release the platform
surface (`SKRenderQueue.cpp:276-279` does so only on `DISPOSE_SURFACE`). (c) `:51-53`: the GDI
fallback on failure leaves the previous chain configured; whether GDI is visible under a live DXGI
flip chain is **to verify** on Windows. *Fix:* release the Dawn side synchronously when a window
surface stops being the peer's surface (dispose the platform surface for `WINDOW` ops on
`FLUSH_SURFACE` too, or add `releasePlatformSurface()` called by the manager), and make
`Win32SKGraphicsConfig.createSurfaceData` return GDI unconditionally.

**R12. `Win32SKSurfaceData.java:105-107, 182-185` — risk (to verify): off-screen surfaces create
Dawn textures without the render-queue lock.** `OffScreen -> platformSurface -> createPlatformSurface
-> device.CreateTexture` runs on the caller's thread while the flusher records and submits on the
same `wgpu::Device`; the window path locks and flushes (`:92-101`), the off-screen path does not,
and the device is not requested with `ImplicitDeviceSynchronization` (`DawnSKPlatform.cpp:103-127`).
*Fix:* take `rq.lock()/unlock()` around `createPlatformSurface`, or request the feature.
*Evidence:* Dawn `docs/dawn/features/implicit_device_sync.md`.

**R13. `DawnSKPlatform.cpp:109-115, 341-347` — risk: no device-lost or surface-lost handling.**
The device-lost callback and the `Lost`/`Outdated` statuses only log; nothing marks the config or
surfaces lost, nothing re-`Configure`s, nothing reaches Java (`isSurfaceLost`,
`InvalidPipeException`, `replaceSurfaceDataLater` as in `D3DScreenUpdateManager.java:325-398`).
After a GPU reset every Skia window stays frozen. *Fix:* a `lost` flag on `DawnSKConfigInfo` set by
the callback, honoured by `SKPlatform_BackendTexture`/`RequestRedraw`, surfaced to Java so the config
is recreated (`Win32GraphicsDevice.displayChanged` already resets `defaultConfig`); re-`Configure`
on `Outdated`.

**R14. `DawnSKPlatform.h:46`, `DawnSKPlatform.cpp:349, 359` — risk: `DawnSKSurface::config` is a
raw pointer whose lifetime rests on Java reachability only.** `DawnSK_DisposeConfig` deletes the
struct every surface of that config points to; safe today only because `Win32SKSurfaceData` keeps
the Java config reachable and the dispose path never dereferences `config`. Becomes a
use-after-free if anything draws to or presents an old surface after a display change once the
Disposer has processed the config first (Disposer order is unspecified). *Fix:* hold
`wgpu::Device`/`wgpu::Queue` by value in `DawnSKSurface` (refcounted handles). **To verify:** the
hand-over after a display change (`:214-219`) re-`Configure`s a `wgpu::Surface` from the old device
with the new one; Dawn should detach the previous chain, but this could not be confirmed from the
headers.

**R15. `ScreenUpdateManager.java:130` vs `D3DGraphicsDevice.java:444-449` — risk (explicit flags
only): `-Dsun.java2d.d3d=true -Dsun.java2d.skia=true` yields silent GDI.**
`D3DGraphicsDevice.getDefaultConfiguration` never calls `super`, so the Skia hook is skipped while
`Win32SKScreenUpdateManager` is installed and falls through to GDI, losing D3D on-screen too. JBR
defaults `d3d` to `false`, so an explicit flag is needed. *Fix:* in `WindowsFlags.initFlags` set
`d3dEnabled = false` when Skia is requested, as OGL and Vulkan do.

### Nits

- `DawnSKPlatform.h:63` — **external reference**: "the row of the coverage matrix this port
  measures". Replace with "D3D11 first, D3D12 as fallback".
- `DawnSKPlatform.cpp:50-57` — `Vulkan` case in `backendName` is dead on this platform.
- `DawnSKPlatform.cpp:244-247, 257-260, 281-282` — the `modes` string feeds a release-level INFO
  trace that fires on every surface creation (every resize). Downgrade to `J2dTraceLn(VERBOSE)`.
- `DawnSKPlatform.cpp:262-267` — on the format/usage failure the chain has already been moved out
  of `previous` and is deleted without `Unconfigure()`, asymmetric with `SKPlatform_DisposeSurface`.
  Check capabilities before the hand-over.
- `DawnSKPlatform.cpp:187-189` — `GetWindowRect`/`GetClientRect`/`ClientToScreen` return values
  unchecked; a destroyed HWND should return null rather than a surface with a chain on a dead window.
- `DawnSKEnvironment.cpp:34-40` — a full D3D device is created and torn down for the description.
- `DawnSKEnvironment.cpp:41`, `Win32SKGraphicsConfig.cpp:41` — `JNU_NewStringPlatform` on a UTF-8
  adapter name decodes with the ANSI code page; use `NewStringUTF` or convert.
- `Win32SKSurfaceData.cpp:23, 41-42` — platform JNI reaches into the shared `SKSDOps` layout to
  read `->platform`; add `SKSurfaceData_PlatformOf(SurfaceDataOps*)` next to `SKSurfaceData_IsSkiaOps`.
- `Win32SKGraphicsConfig.java:85-90, 149-160, 164-180, 200-209` — `SKContextCaps`,
  `createCompatibleVolatileImage`, `getColorModel` (with a copied `REMIND`) and `SKImageCaps` are
  verbatim WGL/MTL copies that are not GPU-API specific and that `MTLGraphicsConfig` carries too;
  candidates for default methods on `SKGraphicsConfig` in `share/`.
- `Win32SKSurfaceData.java:137-149` — `peer.getColorModel()`/`peer.getBounds()` evaluated twice.
- `Win32SKScreenUpdateManager.java:29-35, 66-70` — Javadoc describes lineage and a false invariant
  (fixed by B1).

### Clean

Flag-off behaviour of all three hooks (`Win32GraphicsDevice.java:219, 312-321`,
`WToolkit.java:641-643`, `ScreenUpdateManager.java:130-131`); present ordering (submit on the same
`wgpu::Queue` before `Present()`, all on the flusher thread); hand-over synchronisation
(`createData` holds the queue lock and flushes before `new Window(...)`); hot-path handles are
RAII; integer sizes are range-checked; JNI reference handling; lock pairing and lock order
(treeLock -> peer -> manager -> rq, the flusher never calls back into the manager); copyright
headers; `DawnSK*`/`Win32SK*`/`SK*` naming.

## 4. Build integration

### Risks

**R16. `lib-skia.m4:102-103` — risk: `--with-skia` on Linux configures but cannot build.**
The Linux branch sets `-DSK_VULKAN` and the gmk has no Linux sources; `libawt_skia` would compile
the `share/` files and fail to link `SKPlatform_*` and `Java_sun_java2d_skia_SKEnvironment_initNative`.
*Fix:* `AC_MSG_ERROR` for unsupported target OSes until a Linux half exists.

### Nits

- `AwtLibraries.gmk:657` — `OPTIMIZATION := LOW` for a library whose CPU paths (Bresenham runs,
  mask staging, LCD conversion, opaque fill, opcode interpretation) are what the perf run measures.
  `libawt_lwawt` is also LOW, so Skia-vs-Metal is even, but neither is representative of a shipped
  `libawt` (HIGHEST). Decide deliberately and record the choice in the PR.
- `lib-skia.m4:64` — `ls -d out/*/ | head -n 1` picks the first `out` directory; an unpacked tree
  with two build types silently selects one. Prefer `out/${SKIA_BUILD_TYPE}-*`.
- `spec.gmk.template:515-516` — `SKIA_INCLUDE_DIR`/`SKIA_LIB_DIR` are substituted and never used by
  make.
- `fetch_skia.sh`, `skia_prebuilt.conf`, `libawt_skia.exports` — no copyright line. The sibling
  `common.sh` has none either, so this follows local precedent; a JBR reviewer may still ask.
- `skia_prebuilt.conf:9` — **external reference** (see section 6).

### Clean

Nothing changes without `--with-skia` (`SKIA_ENABLED=false`, the gmk block is skipped, no Java
class is touched by the build flag). `-std=c++17` after `CXXFLAGS_JDKLIB` is fine on clang. The
third copy of `AccelGlyphCache.c` (libawt_lwawt and libfontmanager have their own) is safe:
`GlyphInfo.cellInfo` chains cross library copies, but `AccelGlyphCache_RemoveAllCellInfos` only
unlinks (`AccelGlyphCache.c:334-392`); `free()` happens only in `AccelGlyphCache_Free` of the owning
copy, so there is no cross-library or (on Windows, `-MT` vs `-MD`) cross-CRT free. `SKSDOps` are
allocated and freed by `libawt`'s `SurfaceData_InitOps`/`SurfaceData_DisposeOps`. The exports list
is correct for the stated Skiko-coexistence goal.

build-file change is needed (the library compiles the whole directory; `libosxapp` is in

### Risks

**R17. `MTLRenderQueue.m:62-73, 185-190` — risk: the gate inspects the current state, not the
pending work.** `canCoalesceCommit` reads `mtlc.composite`/`mtlc.paint` when the `RESET_PAINT`
(or post-`MASK_OP`) decision is made, but the command buffer may hold work encoded under another
state: `SET_ALPHA_COMPOSITE`, `SET_XOR_COMPOSITE` and `SET_COLOR` never commit (`:617-630,
791-794`; `CheckPreviousOp` returns early for them). Reachable: XOR fill -> `drawImage`
(`validateContext` with `comp=SrcOver`, `paint=null`) -> `RESET_PAINT` finds SrcOver + colour
paint and skips the commit the XOR draws needed. Whether this is visible is empirical (the XOR
shader reads the attachment, so the sensitivity is to pass boundaries). *Fix:* a sticky
per-command-buffer flag set whenever an op is encoded while `!canCoalesceState(mtlc)`, tested in the
decision, cleared on both commit paths and in `MTLRenderQueue_reset`.

**R18. `MTLOptions.m:49-53` + `MTLGlyphCache.m:103-113` — risk: `glyphCacheSize` is unvalidated.**
A value above the device limit makes `newTextureWithDescriptor:` return nil; `glyphCacheInitWidth:`
does not check and returns YES, `replaceRegion:` on nil is a silent no-op, cached text vanishes.
Opt-in only. *Fix:* accept multiples of 32 within [32, 16384] (or `{512, 1024}`), otherwise log and
use the default; return NO from `glyphCacheInitWidth:` on a nil texture.

## 7. Overall assessment

**(a) CI performance run.** Ready on macOS once R3 (unbounded opaque-conversion buffer; a
pathological but legal `drawImage` can pin 1 GiB) and the `SKContext.forConfig` lookup nit are
addressed — the latter is the one Java-side cost per primitive batch that Metal does not pay, and it
would skew the comparison. R1/R4 are latent and R5-R9 do not affect throughput. Decide the
`OPTIMIZATION` level deliberately (both pipelines at LOW is even but not representative). On
Windows, fix B1 (every window leaks a swap chain; a long perf session will exhaust them) and B2 first,
and treat R10/R13 as known: a device loss during the run will freeze the windows rather than fail
loudly. The macOS presentation race (R7) can produce a torn frame in a screenshot-based comparison;
it does not affect timings.

**(b) First pull request of the Metal switches commit.** Small, opt-in, defaults provably unchanged,
build untouched, precedent-following property code. Before opening it: fix R17 (sticky per-buffer
flag, or document the gate as a heuristic) and R18 (validate `glyphCacheSize`, nil-texture check),
remove the external/dated references in `MTLRenderQueue.m:57-61` and `MTLOptions.h:22-25`, drop the
dead `MTLTR_CACHE_*` macros and the non-ASCII characters, and settle the licence-header form for new
files in `libawt_lwawt`. With those it is a low-risk, reviewable PR; without R17/R18 it is still
shippable because every change is opt-in, but a reviewer will raise both.
