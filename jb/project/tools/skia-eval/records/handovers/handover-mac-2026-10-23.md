## Contract changes you need to pick up (blind edits to `MTLSKPlatform.mm`, not compiled here)

- `int SKPlatform_GlyphPlacementGrid(const SkTypeface *typeface, float pixelSize, float displayScale)` — positions per **device** pixel; Windows divides DirectWrite's per-DIP grid (4 symmetric / 8 natural) by the display scale; the macOS stub returns 0 (CoreGraphics positions continuously, the JDK's variants stay).
- `bool SKPlatform_SmoothedGlyphMask(const SkTypeface *typeface, uint16_t glyph, const SkMatrix &glyphToDevice, float displayScale, int luminance, bool lcd, float strokeWidth, float originX, float originY, int width, int height, uint8_t *mask)` — `displayScale` is new (after `glyphToDevice`); `lcd` and `luminance == -1` (linear coverage) came with the previous round. The macOS definition only has the new parameter in its signature; it is unused there (CoreText takes the device transform).
- `SKFontScaler.createContextNative(pScaler, matrix, aa, fm, boldness, italic, deviceScale, displayScale, grayMode, grayDarkening, grayLuminance)` — `displayScale` is the scale of `FontStrikeDesc.devTx` (2 at 200 %), set by `FileFontStrike` through a new `FontScaler.createScalerContext(matrix, aa, fm, boldness, italic, luminance, displayScale)` overload; `SKFontStrike` (your CFont path) passes its `deviceScale` for both, which is the same number there. Semantics kept apart on purpose: `deviceScale` = the space whole-pixel advances are rounded in (user space on macOS, device space on Windows); `displayScale` = the platform's DIP scale.

## Why (short)

Two per-DIP effects in DirectWrite/Direct2D made the 2× sheets differ from native by mean 45 while 1× matched within max 4–5:
1. the horizontal placement grid is per DIP (2 positions per device pixel at 200 %);
2. Direct2D's natural-symmetric grayscale samples the outline on a 4 × 4 grid per DIP — 4 coverage steps per device pixel at 200 %, 16 at 100 % — with the same total ink and blend parameters, and DirectWrite's own analysis textures are DPI-invariant. So the smoothed route must draw on a Direct2D target at the display's DPI in DIPs (it does now); linear coverage cannot reproduce the 200 % look.
Both with red-first tests (`PlatformPlacementGridTest` 2× cases, new `PlatformSmoothingSampleGridTest`). After the fix: 2× `platform` vs native, regular/italic/bold rows of Segoe UI, Consolas, JetBrains Mono and Inter regular max 4–6, mean 3.7, 0 px > 32.

## Later the same evening (commit `JBR-10654 Skia: DirectWrite's placement grid has two regimes by display scale, not a per-DIP count`)

- The per-DIP model was wrong. DirectWrite's symmetric mode has two regimes by display scale: quarter pixels and 4 × 4 samples up to 1.79, half pixels and 2 × 2 samples from 1.81 on, whatever the pixel size; the natural mode keeps eighths at every scale. The grid hook now returns 8 / 4 / 2 by a 1.8 threshold; 125 % and 150 % are exact, not approximations. Tests red → green at 1.25× and 1.5×; sheets at 1.25× and 1.5× match native within max 4–6 in every non-underlined row.
- The 2× style-row residual is Direct2D's own: it renders some glyphs of slanted faces differently inside a multi-glyph run than alone (no translated single-glyph rendering matches, not an overlap effect), from scale 1.8 on. Java matches Direct2D's glyph-by-glyph output exactly; left as a documented residual (see ledger).
