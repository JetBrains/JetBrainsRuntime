**TDR on D3D12: Skia does not come back, the window stays on GDI and its configuration is recreated every half second; D3D11 recovers in about a second**

- `smoke/run-tdr.ps1 -Arms skia,skia-d3d12` (the user's elevated run; `build/skia-eval-out/tdr-d3d12`).
  The script first failed: `-File` passed `-Arms skia,skia-d3d12` as one string (no arm ran), and
  `DisplayChangeProbe`'s stderr stopped it under `ErrorActionPreference = Stop`; it also ran without
  the pipeline-cache property and created an empty `~/.java/skia/28-internal` (removed). Fixed in
  the kit (commit above), together with run-ide.sh and profile-flush.ps1, which could have done the same.
- D3D11 (`skia`): TDR forced at +20 s; one frame black at t = 24.4 s (configuration replaced),
  green on the new configuration from t = 25.3 s at 64 fps to the end; exit 0. As on 2026-10-22.
- D3D12 (`skia-d3d12`): at t = 24.0 s the device is lost, the window falls back to GDI and stays
  green at about 42 fps, but Skia never returns: every new device fails with
  `D3D12 create command queue failed with DXGI_ERROR_DEVICE_REMOVED (0x887A0005)` (3666 times in
  44 s) and swap chains with `Creating the IDXGISwapChain1 failed with 0x80070005` (1749); the
  configuration is recreated every 0.5 s (`incompatible` 1748 at the end), the surface alternating
  between `Window(lost)` and `GDIWindowSurfaceData`. Exit 0, no crash.
- Two findings:
  1. D3D12-specific, a hypothesis to verify: D3D12 hands out one device per adapter, the same
     object while any reference to it lives; the lost device's Graphite contexts and surfaces still
     hold it when recovery asks for a new one, so D3D12 returns the removed device. D3D11 creates a
     fresh device. A fix would release every reference to the old device (contexts, surfaces,
     the Dawn device and adapter) before creating the new one.
  2. Shared code, also on D3D11 whenever a device stays lost: `Win32SKScreenUpdateManager` gives
     up after three recoveries in a row (`MAX_RECOVERY_ATTEMPTS`), but resets the count whenever a
     Skia window surface is created, and here a surface is created on each new configuration before
     its device turns out to be lost, so the limit never trips and the churn goes on. The count
     should reset only once a surface on the new device has presented. Candidate for a jtreg test
     with a simulated loss (a test hook that marks the device lost), since a real TDR needs elevation.
- `DisplayChangeProbe` (D3D11): exit 0, as before.
- Verdict on D3D12 for now: functional and pixel-identical, 3 % slower to paint, and it does not
  survive a device loss. The default stays D3D11; `sun.java2d.skia.dawnBackend=d3d12` stays an
  evaluation option.

**The recovery counter fixed (finding 2 above), test first**

- `Win32SKGraphicsConfig.simulateDeviceLoss(persistent)` (test hook; native
  `DawnSK_SimulateDeviceLoss`): marks the devices lost; `persistent` also marks each new device lost
  once it has a window surface, which reproduces the D3D12 TDR pattern without elevation.
- `SkiaDeviceLossRecoveryTest transient|persistent`: before the fix transient passed (one
  configuration change, back on Skia) and persistent failed (100 configurations in 10 s, the last
  change 0.5 s before the end). After it both pass: transient as before; persistent three
  recoveries within 0.1 s of the loss (configurations `28c530c4`, `3908de45`, `1998d48c` in a
  temporary trace), the fourth refused, the window on `GDIWindowSurfaceData` and painting
  (31 paints in 0.5 s), quiet for the remaining 10 s.
- The fix (`Win32SKScreenUpdateManager.recover`): the count resets only when the previous recovery
  has held for 30 s, not when a surface could be created; a loss counts once however many
  configurations it takes with it (no new recovery while one is queued), so one TDR on several
  monitors cannot use up the attempts by itself.
- Skia jtreg set on the fixed image: 48 run lines pass plus both lines of the new test (run alone
  after the kit's runner learned `sun.awt.windows` and `ONLY=<test>`; the test now stops its
  repaint timer, which had kept the VM alive past `PASSED`); the known `SkiaFontScalerMetricsTest`
  aside.
