# Raw records: Windows x64 hardware machine (x64hw), 2026-10-22

Summary: first session on real Windows x64 hardware (Ryzen 5 5600G, RTX 3080 Ti). Phase 0 (build
and environment) in progress; no correctness or performance numbers yet.

**2026-10-22 — Machine and build environment**

- CPU: AMD Ryzen 5 5600G (6 cores, 12 threads), PBO off. RAM: 2 x 8 GB G.Skill F4-3200C16-8GVKB at
  DDR4-3200 16-18-18-38 (DOCP, 1.35 V), VDDCR SOC pinned to 1.15 V. Board: ASUS ROG STRIX B550-I
  GAMING, BIOS 4304 (AGESA ComboV2 PI 1.2.0.12).
- GPUs: NVIDIA GeForce RTX 3080 Ti (Zotac, VBIOS 94.02.71.00.B2, 350 W limit, PCIe 3.0 x16, driver
  617.14 / 32.0.16.1714). The CPU's integrated Radeon (Vega 7) is present in hardware but disabled by
  the firmware while the display hangs on the dGPU (Integrated Graphics: Auto); not visible to
  Windows in this session.
- Display: one LG 27GN950, 3840 x 2160 at 143.9 Hz, 200 % scale, on the RTX 3080 Ti (DisplayPort).
- Windows 11 Pro 26H2, build 26300; power plan High performance.
- Build: branch `manuel.unterhofer/JBR-10654-skia-backend-x64hw1` = shared tip `309b521cf1e` plus the
  hand-over commit. Prebuilt Skia `m156-24300fbbcb` (windows x64, verified by `fetch_skia.sh`).
  MSYS2 2026-09-27 (not Cygwin) with make 4.4.1 and autoconf; VS 2026 Build Tools (MSVC 14.51,
  cl 19.51.36252); boot JDK Temurin 27+35; `--with-toolchain-version=2026 --with-skia=<prebuilt>`.

**2026-10-22 — The Windows build breaks on the font-scaler commit**

- `03bd323e5c2` (font scaler on the platform's Skia font host) does not compile on Windows x64 with
  MSVC 14.51: `DawnSKPlatform.cpp` returns `sk_sp<SkTypeface>` and `sk_sp<SkFontMgr>` from its stubs
  but sees only the forward declarations in `SKPlatform.h` (error C2027 in `SkRefCnt.h`, line 151).
  Fix: include `include/core/SkFontMgr.h` and `include/core/SkTypeface.h`, as a `fixup!` of
  `03bd323e5c2` on this branch. No jtreg test: the build is the test.
- Disagreement with HANDOVER.md, section 2: it lists the Skia font scaler as "DirectWrite host on
  Windows"; on this tip the Windows functions are stubs that return `nullptr` ("joins when the text
  track reaches Windows"), so `-Dsun.java2d.font.scaler=skia` falls back to the JDK's scalers here.
  The `skia-scaler` arm therefore measures nothing new on Windows.

**2026-10-22 — Adapter, and the default pipeline is not Direct3D**

- `SkiaSmoke`: `Skia m156 Graphite/Dawn on NVIDIA GeForce RTX 3080 Ti (D3D11)`; `WindowSurfaceProbe`:
  `Win32SKGraphicsConfig`, `Win32SKSurfaceData$Window`, scale 2.0. Dawn picked the dGPU while the
  iGPU was also active (Integrated Graphics forced on, second display extended on HDMI).
- Disagreement with HANDOVER.md, section 6: the `d3d` arm ("nothing, the Windows default pipeline,
  Direct3D 9") does not select Direct3D on this branch. `WindowsFlags` defaults `sun.java2d.d3d` to
  `false` since JBR-7051 (`565865d2f89`, 2024-05-15); with no flags a window paints with
  `GDIWindowSurfaceData` on `Win32GraphicsConfig`, the same as the `software` arm. Direct3D 9 needs
  `-Dsun.java2d.d3d=true`. The arms on this machine: `d3d` = `-Dsun.java2d.d3d=true`, `software` =
  `-Dsun.java2d.d3d=false`.

**2026-10-22 — A real TDR (`dxcap -forcetdr`) under TdrProbe, and DisplayChangeProbe**

- Kit additions: `smoke/TdrProbe.java` (a window animating at about 60 Hz through a cached
  VolatileImage; logs every 0.5 s fps, what the screen shows in the window's centre, surface class,
  configuration, VolatileImage validate counts; captures every 5 s) and `smoke/run-tdr.ps1` (elevated:
  TdrProbe per arm with a forced TDR after 20 s, then DisplayChangeProbe, System events). Display:
  one display on the RTX 3080 Ti, `uiScale=1`, 60 s per arm, n = 1.
- Skia: TDR forced at +20.0 s; the nvlddmkm 153 events follow; at about +23.5 s the device-lost
  callback: `DawnSK: device lost (1): D3D11 command queue signal fence failed ... Device removed
  reason: DXGI_ERROR_DEVICE_RESET (0x887A0007)`. A new device comes up at about +24 s, but
  configuring the window's surface on it fails: `DawnSK: swap chain configuration failed (2): D3D
  SwapChain cannot switch between D3D Devices`, `DawnSK_CreateSurface: no swap chain for HWND ...`;
  that sample (+24.3 s) shows BLACK at 4 fps. A second configuration (`shared device`) presents at
  +25.2 s: GREEN, 64 fps to the end (+68 s). VolatileImage: 2 x IMAGE_INCOMPATIBLE, recreated and
  drawn. No crash, exit 0. Black for about one sample (0.5 to 1 s).
- Comparison arm (no flags, so GDI, see above): BLACK from +24.6 to +26.0 s, then GREEN at 62 fps; no
  VolatileImage loss reported. The Direct3D 9 arm proper (`-Dsun.java2d.d3d=true`) has not run yet.
- The whole adapter resets: the desktop wallpaper and Windows Terminal went blank for a while too.
- Candidate defect, not yet a test: after the loss the window's existing Dawn surface is
  reconfigured on the new device, which D3D refuses; a surface created afresh for the new device
  would probably present one frame earlier. A jtreg test needs a real TDR (elevated, `dxcap`), so it
  does not fit the jtreg set as is; left to the user.
- Probe gap: `deviceLost` never read `true`; the frame's configuration was replaced before the 0.5 s
  sample saw the old one lost.
- `DisplayChangeProbe` (Skia, no TDR): each `displayChanged()` gives a new `Win32SKGraphicsConfig`
  on the shared device; the old VolatileImage validates to 2 (IMAGE_INCOMPATIBLE); the blit of the
  old image into a new one is drawn (`ffff0000`), as expected for a shared device.

- Direct3D 9 arm (`-Dsun.java2d.d3d=true`, second elevated run, n = 1): before the TDR
  `D3DWindowSurfaceData` on `D3DGraphicsConfig`, adapter 0 = RTX 3080 Ti on `\\.\DISPLAY6`. After it:
  the surface reports lost at +23.9 s, BLACK at +24.4 and +25.2 s, GREEN from +25.7 s, but on
  `GDIWindowSurfaceData` / `Win32GraphicsConfig` to the end: Direct3D does not come back for the
  process. VolatileImage: IMAGE_INCOMPATIBLE once, contentsLost once. No crash, exit 0. Skia, by
  contrast, stays on Skia (a new device) after the same TDR.
- In every arm (skia, no flags = GDI, d3d) the window's scale jumps from 1 to 2 across the TDR: the
  probe runs with `-Dsun.java2d.uiScale=1`; before the TDR its content pane is 614 x 409 and the
  96-pixel square is 96 device pixels; after it the content pane is 308 x 205 (user space) and the
  square covers 192 device pixels, so the window renders at the OS scale (200 %) from then on. Not
  Skia-specific. A display change in software (`Win32GraphicsEnvironment.displayChanged()` on the EDT,
  `uiScale=1`) does not reproduce it: device and frame stay at 1.00. Hypothesis, unverified: the real
  reset also brings `WM_DPICHANGED` (the compositor restarts), whose handling takes the OS DPI past the
  `uiScale` override. Consequence for this kit: a pixel tool that lives through a display change
  captures at the wrong scale; none of the planned runs force one.

**2026-10-22 — jtreg Skia run lines: 26 of 27 pass; eviction ratios 1.7 (gray) and 2.0 (LCD)**

- `smoke/run-jtreg-skia.sh` on the image of `fbc6f937bfb` (tip plus the include fixup), one display on
  the RTX 3080 Ti. The runner needed three repairs to stand in for jtreg on this branch: the tests
  share `PipelineComparison` through `@library ..` (now `-sourcepath Graphics2D`), need
  `sun.java2d.skia` exported and `sun.font` opened (`@modules`), and `GlyphAtlasEvictionThroughputTest`
  is written `@run main/othervm/timeout=120`, which the old pattern skipped silently (that is why
  the eviction ratio was missing from the first pass).
- 26 PASS: `AnalyticShapeEdgeTest` (analytic, marlin, strokes=java), `GradientCycleTest`,
  `NonAAGeometryTest` (msaa 1; skia shapes msaa 4), `PipelineSelectionTest` (with vulkan=true and with
  opengl=true: `Win32SKGraphicsConfig`, `Win32SKSurfaceData$OffScreen`), `TranslucentSourceTest`,
  `XorModeTest`, `FallbackGlyphsTest`, `GlyphAtlasEvictionTest` (gray, lcd, lcd accumulate),
  `GlyphAtlasEvictionThroughputTest` (gray, lcd), `GlyphVectorBoundsTest`, `LcdTextBackgroundsTest`,
  `LcdTextDisposeTest`, `LcdTextLayersTest` (blend, twopass, accumulate each).
- `GlyphAtlasEvictionThroughputTest`, n = 1 each: grayscale 600 glyphs 0.77 ms, 1500 glyphs 1.29 ms,
  **ratio 1.7**; LCD 600 glyphs 1.11 ms, 1500 glyphs 2.17 ms, **ratio 2.0**. The VM had 10.3 / 5.9
  (Windows limit 16), Metal 2.5: on real hardware the eviction cost is in Metal's range, the VM's
  numbers were its upload path.
- 1 FAIL: `SkiaFontScalerMetricsTest` (`-Dsun.java2d.skia=true`): `IllegalArgumentException: Can not
  get java.lang.String field sun.font.PhysicalFont.platName on sun.font.CompositeFont` at line 86. On
  Windows the logical fonts resolve to `CompositeFont`, which the non-CoreText branch reads as a
  `PhysicalFont`. The test means to skip where the font host is missing ("Nothing to test where the
  Skia backend or its font host is unavailable"), but `SKFontScaler.isAvailable()` returns
  `SKEnvironment.isSkiaEnabled()` and so says true on Windows, where `SKPlatform_FontManager()` is a
  stub returning `nullptr`. The product side degrades: `FontScaler.getScaler` catches the
  `IllegalArgumentException` of `SKFontScaler.forFile` (no typeface) and falls back to FreeType, one
  exception per font. Two candidate fixes, both left to the user (text track, interface): make
  `isAvailable()` ask the native side whether a font host exists, and let the test take a
  composite's slot 0 or skip composites. The failing test is the red test for either.
